## 发现与处置

### P1（已修复）

| 发现 | 处置 |
| --- | --- |
| 旧 `PlanReceipt.descriptor_removals` 在 Core 中直接 `hub.remove`，Host 校验也不覆盖该字段：任一 provider 的回执可删除其他 provider 的 descriptor | Core 回执同步不再删除；Host actor 以与 invalidation 相同的 provider/generation 栅栏应用旧字段（`invalidate_legacy_receipt_removals`），越权删除返回 `resource.generation_mismatch` |
| ServiceHost `plugin.reload` / 部署切换用启动时 `self.config` 重建 bootstrapper，`reconfigure_plugins` 之后的插件配置被静默回滚 | `reload_catalog_unlocked` 必须接收 `current_config()` |
| `TaskWait` 在 async 控制 handler 中同步阻塞，`timeout_ms` 无上限 | 改为 async，等待移到 blocking pool；新增 `MAX_TASK_WAIT_TIMEOUT_MS`（60 s），超限返回 `bad_request` |
| Tauri 同步 command（call / task_result / peek）在 UI 线程上无限等待任务 | 改为 async command，经 `spawn_blocking` 等待 |
| Agent subagent / next-edit / local runtime 用 `yield_now` 或 1 ms sleep 自旋等待子任务；QQ 投递 5 ms 轮询 | SDK `TaskSubmitter::wait_outcome` / `RuntimeClient::wait_outcome`：Host actor 客户端事件驱动（`WaitTaskStates`），其余客户端有界退避；所有调用点改用它 |

### P2（已修复）

- 调度失败直接结束 Host actor 主循环：改为记录 `scheduler_failures` 指标后继续服务。
- 本地 typed payload 序列化失败会在入池时 panic actor：`TaskPayload::try_wire_len` /
  `try_as_value` 让 TaskPool 返回结构化错误，同时直接从类型体计算 wire 长度。
- 异步执行器在 Tokio worker 上阻塞投递完成事件：`ActorSender::send_nonblocking`，
  满队列时按序溢出到受 admission 约束的侧队列。
- SDK 分组批处理 lane panic 让整批失败（含已提交条目）：panic 只失败本 lane 未完成条目。
- reload 生命周期错误是字符串：改为结构化 `RuntimeError`。
- `HostServiceRegistry` 三把锁 + 锁外检查 `frozen`：合并为单锁，freeze 与注册原子。
- reload drain 期间在 async worker 上持有 std Mutex：`block_in_place` 包装（多线程运行时）。
- `MUTSUKI_TEST_ALLOW_EMPTY_TOKEN` 可在生产构建关闭控制面鉴权：删除。
- `save_deployment_state` 先删旧文件再 rename：改用 `write_managed_file_atomically`
  （rename 覆盖 + 父目录 fsync），runtime lock 同样处理。
- Distributed `ha_control` / `resource_catalog` / `content_store` 原子写不 fsync 父目录：
  统一 `durable_io::replace_file`。
- `FixtureControlHandler`（硬编码 token）进入生产 crate：移到 `testkit` feature，仅 dev-dependency 启用。
- 公开 IPC 客户端暴露 `From<&ServiceConfig>`：删除，服务端侧 `local_control_client_config` 承担转换。
- Tauri 复制 SDK backend 描述符逻辑且取值不同：SDK `ensure_plugin_backend_descriptors`
  为唯一 owner，进程外部署（Process/Python）统一 `drain_and_swap`。
- Tauri 关闭直接 abort：`shutdown_with_drain` + `shutdown_drain_ms`（默认 2 s），
  `HostRuntime::wait_until_idle` 事件驱动等待；ServiceHost drain 改用同一接口。
- Bilibili runner 在 Orchestration 域做阻塞 HTTP：声明 `Io`；配置共享改为 `Arc`，
  轮询时清理已删除订阅的调度状态。
- 产品配置把畸形 `runtime_config` 静默回退为旧值/默认值：解析失败返回 `ApplyRejected`。
- `SandboxAwareOpenApiRunner` 位于 Host 集成包（违反“禁止再往里加业务 Runner”）：移入 `mutsuki-bot-sandbox`。
- 删除绕过 actor 的公开 API：`LocalTaskClient`、`impl RuntimeClient for Arc<Mutex<CoreRuntime>>`、
  `CoreRuntime::resources_mut`、`HandlerBindingRegistry::register_authorized`、SDK 实验性 deprecated helper、
  Agent facade 的 deprecated 重导出。
- 5 个在用但未登记的错误码登记到 contracts，并同步 Python 镜像与契约表。

### 性能（已优化）

- 调度热路径：不再为构造 `TaskHandle` 克隆整条 Task；payload 字节数用计数 writer，不分配编码缓冲；
  每轮调度预计算各 runner 运行批次数，替代 O(R·T) 扫描；完成路由不再克隆 `RunnerDescriptor`；
  `query_protocol` 二分定位。
- Kernel commit/event 任务保持本地 typed payload，消除 JSON 往返；行布局解码不再先克隆 `Value`。
- Link：`FramedConnection`/`LocalConnection` 提供可等待的 `send`/`receive`/`close_and_flush`，
  替换 4 处轮询循环（含关闭后仍轮询到超时的问题）；写端 `BufWriter` 合批，队列排空才 flush；
  ServiceHost Link 控制服务按连接并发处理，删除“sleep 让回复发出”的写法。
- 分布式资源目录按引用序列化；Web RPC 参数移动而非两次深拷贝。
- Agent：会话 append 原地追加（失败回滚），去掉两次全量克隆；code-index 正则只编译一次；
  web-search 复用连接池；MCP HTTP 接收不再 1 ms 轮询。

## 保留与后续

- `legacy_protocol_class`：多数 manifest 仍依赖默认归类，保留。
- Agent facade 插件 crate 仍承载真实 runner，只删除了重导出。
- Bilibili/Workshop 仍通过同步 secure-fetch 下载媒体（已移出 Orchestration 域）；迁移到
  `mutsuki.std.io.http` + TaskAwait 续延需要改写 Runner 流程，单独处理。
- 产品配置的“文档 → owner 配置”反向映射仍在产品 crate，应迁到 owner `config.rs`。
- Agent 会话持久化仍是每次 append 写整份 JSON；增量存储需要 SQLite schema 变更。
- Host actor 每轮仍线性扫描运行中任务求最近截止时间（运行集受池容量约束）；如运行集扩大再换最小堆。
- SDK 分组批处理每批 `thread::scope` 起 lane 线程；仅在 `parallelism_limit > 1` 时发生。
- 评估后未合并：`reconfigure_plugins` 与整目录 reload 的事务步骤相似但回滚/目标集合不同，
  合并需要先补齐两者的故障注入测试；OpenAI/Anthropic 重试循环头部与错误映射各异，
  adapter-api 也不持有 HTTP 客户端；三份 `control_result!` 宏错误语义不同（协议错误、
  类型化错误、测试 panic）；Tauri 插件发现不复用 `service-plugin-loader`，以免 Host 之间互相依赖。
- Bilibili（4.7k 行）、`bot-state-db`（4.1k 行）、`agent-plugin-git`（3.4k 行）仍是单文件，
  拆分属于纯机械搬迁，建议在对应功能改动时按职责逐步拆。
- `MemoryConfigProvider` 的 `apply_mode` 字段未被读取，移除需要改动公开构造签名，留待配置 API 版本调整。
